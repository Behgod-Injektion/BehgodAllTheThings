### تبدیل نوع داده (Type Conversion)

قبلاً دیدیم که `int`، `float` و `str` نام نوع‌های داده در Python هستند. اما یک نکتهٔ جالب وجود دارد: این نام‌ها فقط برای مشخص کردن نوع داده استفاده نمی‌شوند؛ می‌توانیم آن‌ها را مثل تابع فراخوانی کنیم و از آن‌ها برای تبدیل یک مقدار به نوع دیگری استفاده کنیم.

برای مثال، فرض کن مقداری از نوع `float` داریم، اما می‌خواهیم آن را به یک عدد صحیح تبدیل کنیم. چه کار باید بکنیم؟

کافی است از `int()` استفاده کنیم:

!!! example "Python"

    ```python
    >>> int(42.9)
    ```

    **Output:**

    ```text
    42
    ```

همان‌طور که می‌بینی، مقدار `42.9` به عدد صحیح `42` تبدیل شده است. اما یک نکتهٔ مهم وجود دارد: هنگام تبدیل `float` به `int`، بخش اعشاری حذف می‌شود و مقدار به سمت صفر بریده می‌شود؛ نه اینکه به نزدیک‌ترین عدد صحیح گرد شود.

برای مثال:

```python
int(42.9)   # 42
int(-42.9)  # -42
```

!!! bug "این رفتار را با عملگر `//` اشتباه نگیر!"
	عملگر `//` به سمت منفی بی‌نهایت گرد می‌کند، اما `int()` فقط بخش اعشاری را حذف می‌کند.

برای تبدیل عدد صحیح به `float`:

!!! example "Python"

    ```python
    >>> float(42)
    ```

    **Output:**

    ```text
    42.0
    ```

به این فرایند **تبدیل نوع (Type Conversion)** می‌گوییم که گاهی با نام **Type Casting** هم شناخته می‌شود ولی این تبدیل نوع دیگر چه فایده هایی برایمان دارد؟

برای مثال، اگر بخواهیم رشتهٔ `'126'` را بر عدد `3` تقسیم کنیم، چه اتفاقی می‌افتد؟

!!! example "Python"

    ```python
    >>> '126' / 3
    ```

    **Output:**

    ```text
    ---------------------------------------------------------------------------
	TypeError                                 Traceback (most recent call last)
	----> '126' / 3

	TypeError: unsupported operand type(s) for /: 'str' and 'int'
    ```

این بار Python خطایی از نوع **TypeError** تولید می‌کند.

اما این خطا چه تفاوتی با `SyntaxError` دارد؟

در `SyntaxError`، ساختار کد با قواعد نحوی زبان سازگار نیست. اما در `TypeError` ممکن است ساختار عبارت کاملاً معتبر باشد، ولی نوع مقادیری که در آن استفاده کرده‌ایم برای عملیات موردنظر مناسب نباشد.

در مثال بالا، عبارت از نظر نحوی مشکلی ندارد؛ اما عملگر `/` نمی‌تواند یک مقدار از نوع `str` را بر یک مقدار از نوع `int` تقسیم کند.
## تبدیل رشتهٔ عددی به عدد واقعی

حالا که فهمیدیم مشکل از نوع داده است، چطور می‌توانیم آن را برطرف کنیم؟

اگر رشته‌ای داشته باشیم که محتوای آن نمایش یک عدد صحیح معتبر باشد، می‌توانیم با استفاده از `int()` آن را به عدد صحیح تبدیل کنیم:

!!! example "Python"

    ```python
    >>> int('126') / 3
    ```

    **Output:**

    ```text
    42.0
    ```

در اینجا ابتدا رشتهٔ `'126'` به عدد صحیح `126` تبدیل می‌شود و سپس عملیات تقسیم انجام می‌گیرد.

دقت کن که نتیجه `42.0` است، نه `42`؛ چون عملگر `/` در Python نتیجهٔ تقسیم را از نوع `float` برمی‌گرداند، حتی اگر حاصل تقسیم یک عدد صحیح باشد.

اما اگر رشته شامل یک عدد اعشاری باشد، چه باید بکنیم؟

برای مثال:

```python
'12.6'
```

آیا می‌توانیم مستقیماً از `int()` استفاده کنیم؟

!!! example "Python"

    ```python
    >>> int('12.5')
    ```

    **Output:**

    ```text
	   ---------------------------------------------------------------------------
	ValueError                                Traceback (most recent call last)
	----> 1 int('12.5')
	
	ValueError: invalid literal for int() with base 10: '12.5'
    ```

خیر! چون `int()` نمی‌تواند رشته‌ای با نمایش اعشاری مانند `'12.6'` را مستقیماً به عدد صحیح تبدیل کند. برای چنین رشته‌ای باید از `float()` استفاده کنیم:

!!! example "Python"

    ```python
    >>> float('12.6')
    ```

    **Output:**

    ```text
    12.6
    ```

پس انتخاب تابع تبدیل به نوع محتوای رشته بستگی دارد:

- اگر رشته نمایش یک عدد صحیح معتبر باشد، از `int()` استفاده می‌کنیم.
    
- اگر رشته نمایش یک عدد ممیز شناور معتبر باشد، از `float()` استفاده می‌کنیم.
    

البته هر رشته‌ای الزاماً قابل تبدیل نیست. مثلاً عبارت زیر:

!!! example "Python"

    ```python
    >>> int('Hello')
    ```
	**Output:**

    ```text
	---------------------------------------------------------------------------
	ValueError                                Traceback (most recent call last)
	----> int('Hello')
	
	ValueError: invalid literal for int() with base 10: 'Hello'
    ```

باعث ایجاد خطای `ValueError` می‌شود؛ چون محتوای رشته نمایش معتبری از یک عدد صحیح نیست.

> پس تا اینجا با سه نوع خطا آشنا شدیم: `SyntaxError`، `TypeError` و `ValueError`. هرکدام به مشکل متفاوتی اشاره می‌کنند و شناخت تفاوت آن‌ها هنگام Debugging حسابی به کارمان می‌آید.

## نمایش اعداد بزرگ (Large Numbers)

تا اینجا با نحوهٔ نمایش اعداد و تبدیل نوع آن‌ها آشنا شدیم. اما فرض کن بخواهیم یک عدد بسیار بزرگ، مثلاً یک میلیون، را در Python بنویسیم.

معمولاً برای خوانایی بیشتر، اعداد بزرگ را با جداکننده‌هایی مثل کاما گروه‌بندی می‌کنیم:

```
1,000,000
```

شاید تصور کنی می‌توانیم همین شکل را مستقیماً در Python بنویسیم:

!!! example "Python"

    ```python
    >>> 1,000,000
    ```

	**Output:**

    ```text
	(1, 0, 0)
    ```

چرا Python به‌جای یک میلیون، چنین مقداری تولید کرده است؟

چون کاما در این موقعیت نقش جداکننده دارد و Python عبارت بالا را به‌عنوان یک **Tuple** شامل سه مقدار صحیح `1`، `0` و `0` تفسیر می‌کند.

پس برای گروه‌بندی ارقام در یک عدد، نمی‌توانیم از کاما استفاده کنیم.

راه‌حل چیست؟

Python راه ساده‌تری در اختیارمان قرار می‌دهد: استفاده از **Underscore** یا علامت زیرخط (`_`) میان گروه‌های ارقام.

برای مثال:

!!! example "Python"

    ```python
    >>> 1_000_000
    ```

    **Output:**

    ```text
    1000000
    ```

در این حالت، Python مقدار را دقیقاً به‌عنوان عدد یک میلیون تفسیر می‌کند. زیرخط‌ها فقط برای خوانایی کد هستند و هیچ تأثیری روی مقدار عددی نهایی ندارند.

بنابراین، اگر بخواهیم اعداد بزرگ را خواناتر بنویسیم، می‌توانیم به‌جای کاما از Underscore استفاده کنیم.

# Debugging

تا اینجا یاد گرفتیم چطور کد بنویسیم، با مقادیر مختلف کار کنیم و عملیات موردنظرمان را انجام دهیم. اما یک سؤال مهم باقی می‌ماند: اگر برنامه آن‌طور که انتظار داریم رفتار نکند، چه کار کنیم؟

گاهی برنامه‌ای می‌نویسی که ظاهراً همه‌چیز در آن درست است، اما نتیجه‌ای که انتظار داری به دست نمی‌آید. گاهی هم برنامه اصلاً اجرا نمی‌شود. در چنین شرایطی باید چطور بفهمی مشکل از کجاست؟

واقعیت این است که برنامه‌نویس‌ها هم اشتباه می‌کنند؛ حتی برنامه‌نویس‌های باتجربه! به خطاهای برنامه‌نویسی **Bug** می‌گوییم و فرایند پیدا کردن و برطرف کردن آن‌ها را **Debugging** می‌نامیم.

اما Debugging فقط یک کار فنی نیست؛ گاهی از نظر روانی هم می‌تواند دشوار باشد.

وقتی مدت زیادی با یک خطای پیچیده درگیر می‌شوی و نمی‌توانی آن را پیدا کنی، ممکن است عصبانی، ناامید یا حتی خجالت‌زده شوی. شاید با خودت فکر کنی: «چرا نمی‌تونم این مشکل ساده رو حل کنم؟» و همین فکر باعث شود بیشتر از قبل تحت فشار قرار بگیری.

اما برای مدیریت بهتر این شرایط، می‌توانی به کامپیوتر مانند یک کارمند نگاه کنی که توانایی‌ها و محدودیت‌های مشخصی دارد.

کامپیوتر چه توانایی‌هایی دارد؟

- سرعت بسیار بالا در انجام محاسبات و اجرای دستورها
    
- دقت در اجرای دستورهایی که دریافت می‌کند
    
- توانایی تکرار یک عملیات بارها و بارها، بدون خستگی
    

اما محدودیت‌هایش چیست؟

- همدلی ندارد.
    
- منظور واقعی تو را از روی حدس و گمان متوجه نمی‌شود.
    
- نمی‌تواند مانند یک انسان، بدون داشتن دستورالعمل مناسب، تصویر کلی مسئله را درک کند.
    

در واقع، کامپیوتر دقیقاً دستورهایی را اجرا می‌کند که برایش تعریف شده‌اند؛ حتی اگر این دستورها با چیزی که تو واقعاً در ذهن داری تفاوت داشته باشند.

حالا اگر مدیر چنین کارمندی باشی، وظیفه‌ات چیست؟ باید یاد بگیری چطور از نقاط قوتش استفاده کنی و محدودیت‌هایش را در نظر بگیری.

درست به همین شکل، هنگام Debugging باید از توانایی کامپیوتر برای بررسی دقیق، اجرای دوباره و مقایسهٔ رفتار برنامه استفاده کنی. در عین حال، باید مراقب باشی **احساساتت مانع تحلیل منطقی مسئله نشوند**.

به‌جای اینکه با دیدن یک خطا سریعاً چند خط کد را تغییر بدهی و امیدوار باشی مشکل حل شود، بهتر است قدم‌به‌قدم جلو بروی:

1. رفتار فعلی برنامه را بررسی کن.
    
2. مشخص کن چه نتیجه‌ای انتظار داشتی و چه نتیجه‌ای دریافت کردی.
    
3. شواهدی جمع‌آوری کن تا بفهمی مشکل از کجاست.
    
4. فرضیه‌ای دربارهٔ علت خطا بساز و آن را آزمایش کن.
    
5. پس از پیدا کردن علت، مشکل را برطرف کن و دوباره برنامه را بررسی کن.
    

در نهایت، چرا باید برای یادگیری Debugging وقت بگذاری؟

چون این مهارت فقط به برنامه‌نویسی محدود نمی‌شود. توانایی پیدا کردن علت یک مشکل، بررسی شواهد و رسیدن به راه‌حل، در بسیاری از فعالیت‌های دیگر هم کاربرد دارد.

یادگیری Debugging ممکن است گاهی ناامیدکننده باشد، اما مهارتی بسیار ارزشمند است. به همین دلیل، در پایان هر فصل کتاب بخشی به این موضوع اختصاص داده شده که پیشنهادهایی برای بهتر Debug کردن ارائه می‌کند.

هدف این پیشنهادها این است که به‌تدریج یاد بگیری هنگام مواجهه با خطا، به‌جای واکنش عجولانه و تغییر تصادفی کدها، مسئله را منظم، منطقی و مؤثر بررسی کنی.
!!! note "یادت باشد"
	 **هدف Debugging این نیست که سریع‌تر کد را تغییر بدهی؛ هدف این است که دقیق‌تر بفهمی چرا کد آن‌طور که انتظار داری کار نمی‌کند.**
